## Aula 43: Git - salvando o projeto
1. O Git é um programa que guarda versões do seu projeto. Como pontos de salvamento num jogo. [cards]
2. E pra quem testa, pra que serve? Se você estragar um teste, volta pra versão que funcionava. E toda empresa usa: é assim que a equipe junta o trabalho de todo mundo. [cards]
3. No terminal do VS Code: git init. Init é iniciar: comece a guardar as versões desta pasta. [editor]
4. Depois: git add ponto. Add é adicionar, e o ponto quer dizer tudo: prepare todos os arquivos pro próximo salvamento. [editor]
5. Pra conferir o que vai entrar, git status. Repara: o node modules, o ponto env e a pasta do login salvo não aparecem. O gitignore está fazendo o trabalho dele. [terminal]
6. E: git commit traço m, e uma mensagem entre aspas, tipo meu primeiro projeto Playwright. Commit é o salvamento, e o traço m é a mensagem dele. [editor]
7. Se for a primeira vez que você usa o Git, ele pode pedir seu nome e seu e-mail. São dois comandos: git config traço traço global user ponto name, e user ponto email. Depois roda o commit de novo. [terminal]
8. E no dia a dia? Terminou um teste e ele passou: faz um commit. E a mensagem diz o que mudou, tipo adiciona teste do carrinho. Daqui a um mês, você vai saber o que tem em cada salvamento. [traducao]
9. Pronto: o seu projeto tem o primeiro ponto de salvamento. Na próxima aula, ele vai pro GitHub. [passo]
10. Te vejo lá! [endcard]

## Aula 44: GitHub - enviando o projeto
1. O GitHub é um site que guarda projetos Git na internet. É a vitrine de quem trabalha com tecnologia. [bigtext]
2. Pra você, ele resolve três coisas: um backup do projeto, se o computador quebrar. Um lugar onde a equipe trabalha junto. E o seu portfólio: quem for te contratar pode ver o seu código funcionando. [cards]
3. Cria uma conta no github ponto com, se ainda não tiver. Depois clica em New repository. Repositório é a pasta do projeto, lá no GitHub. Dá o nome e cria, sem marcar nenhuma opção, porque o seu projeto já tem os arquivos dele. [github]
4. O GitHub mostra os comandos. No terminal: git branch traço M main. Branch é ramo: uma linha de versões do projeto. Esse comando dá o nome main pro ramo principal. [editor]
5. Depois: git remote add origin, e o endereço do seu repositório. Remote é remoto: avise o Git que existe uma cópia lá no GitHub, chamada origin. [github]
6. E o envio: git push traço u origin main. Push é empurrar: mande o projeto pro GitHub. O traço u liga a sua main com a main de lá, e nas próximas vezes basta git push. [editor]
7. Na primeira vez, o Git pode abrir o navegador pra você entrar na sua conta do GitHub. É normal: faz o login e volta pro terminal. [cards]
8. Atualiza a página do GitHub: seu projeto está lá. E repara: nem o ponto env, nem a pasta do login salvo subiram. [github]
9. E daqui pra frente, o ciclo é sempre esse: add, commit e push. E o GitHub fica igual à sua máquina. [traducao]
10. Na próxima aula: os testes rodando sozinhos no GitHub. [passo]
11. Te vejo lá! [endcard]

## Aula 45: GitHub Actions - os testes rodando sozinhos
1. E se o GitHub rodasse os seus testes sozinho? É isso que o GitHub Actions faz. [bigtext]
2. Por que isso importa? Sem ele, alguém precisa lembrar de rodar os testes. Com ele, toda vez que alguém manda uma mudança pro repositório, os testes rodam sozinhos. E em muitas empresas os testes ficam junto com o código do site: aí cada mudança no site passa pelos testes antes de chegar no cliente. [compare]
3. O Playwright já criou esse arquivo lá no começo: ponto github, workflows, playwright ponto yml. [editor]
4. Lendo em português: quando houver um push ou um pull request na main, use uma máquina Ubuntu, instale tudo e rode os testes. Esses quandos são os gatilhos do arquivo. [traducao]
5. Pull request é quando alguém da equipe pede pra juntar uma mudança na main. Os testes rodam antes, e se ficarem vermelhos, a mudança espera o conserto. [cards]
6. E dá até pra agendar: rodar todo dia de madrugada, mesmo sem ninguém mexer. É assim que um teste aparece falhando às seis da manhã, como na aula do trace. [cards]
7. Só falta uma coisa: o ponto env não foi pro GitHub, então lá os testes não sabem o usuário e a senha. [cards]
8. No GitHub: Settings, Secrets and variables, Actions, New repository secret. Cria o SAUCE underline USER e o SAUCE underline PASSWORD. Secret é segredo: ninguém consegue ver o valor depois. [github]
9. No yml, no passo que roda os testes, um env que entrega esses segredos pros testes. [editor]
10. Traduzindo: SAUCE USER, dois pontos, e cifrão chaves chaves secrets ponto SAUCE USER. Pegue o valor guardado no cofre do GitHub, e entregue pros testes com esse nome, igual o ponto env fazia. [traducao]
11. Manda pro GitHub com git push e abre a aba Actions: olha os testes rodando lá. [gh_actions]
12. Verde: passou. E no fim tem o relatório pra baixar, porque esse arquivo tem o passo que guarda ele. [gh_actions]
13. E se ficar vermelho? O GitHub te avisa por e-mail. Você baixa o relatório, abre o trace, o print e o vídeo, como nas aulas 28 e 30, e anexa no card do bug. [cards]
14. Fechamos o projeto! Tem bônus: testes de API. [passo]
15. Te vejo lá! [endcard]

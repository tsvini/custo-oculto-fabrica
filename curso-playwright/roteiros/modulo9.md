## Aula 43: Git - salvando o projeto
1. O projeto está pronto. Agora, a pergunta: como guardar ele do jeito certo, de um jeito que dá pra voltar atrás se alguma coisa quebrar? [bigtext]
2. Sem nenhuma ferramenta, o que muita gente faz é copiar a pasta. Projeto final. Projeto final dois. Projeto final agora vai. Depois de uma semana, ninguém sabe qual é qual, nem o que mudou de uma pra outra. [cards]
3. O Git resolve isso. Ele é um programa que guarda a história do seu projeto, sem copiar pasta nenhuma. Quando você manda, ele tira uma foto de como os arquivos estão naquele momento, e guarda todas as fotos, em ordem. [cards]
4. Cada foto dessas tem um nome: commit. Pensa nos pontos de salvamento de um jogo. Você salva antes da parte difícil, e se der errado, volta pro ponto salvo. [traducao]
5. E uma confusão muito comum: Git e GitHub não são a mesma coisa. O Git é o programa no seu computador, aquele que você instalou na aula cinco. O GitHub é um site, onde você guarda essa história na internet. Ele é a próxima aula. [compare]
6. E pra quem testa, pra que serve? Se você estragar um teste, volta pra versão que funcionava. É assim que a equipe junta o trabalho de todo mundo sem um apagar o do outro. E quase toda vaga de QA pede Git. [cards]
7. Salvar com o Git tem sempre três passos. Primeiro, você muda os arquivos, que é o que você já faz. Segundo, o git add: você escolhe o que vai entrar na foto. Terceiro, o git commit: você tira a foto, com uma legenda dizendo o que mudou. [cards]
8. Agora na prática. Tudo é feito no terminal do VS Code, aqui embaixo. Antes de começar, confere o caminho antes do cursor: ele tem que terminar com o nome da pasta do projeto, igual na aula oito. [editor]
9. Se é a primeira vez que você usa o Git nesse computador, ele precisa saber quem você é, porque toda foto leva o nome de quem tirou. São dois comandos: git config traço traço global user ponto name, e o seu nome entre aspas. E user ponto email, com o seu e-mail. Só uma vez por computador. E uma dica: usa o mesmo e-mail que você vai usar na conta do GitHub, na próxima aula. Assim, lá no seu perfil, cada commit aparece como seu. [terminal]
10. Agora sim: git init. Init é iniciar. Ele avisa o Git: a partir de agora, guarde a história desta pasta. [editor]
11. Ele criou uma pasta escondida chamada ponto git. É lá que ficam todas as fotos. Você não precisa mexer nela, nunca. E o git init é feito uma vez só por projeto. [cards]
12. Agora, git status. Status é a situação: o Git te conta o que ele está vendo. Repara: tudo em vermelho, debaixo de untracked files, arquivos não rastreados. Ou seja: o Git viu os arquivos, mas eles ainda não vão na foto. [terminal]
13. Passo dois: git add ponto. Add é adicionar, e o ponto quer dizer tudo. Prepare todos os arquivos que mudaram pra próxima foto. [editor]
14. Roda o git status de novo. Agora está tudo verde, debaixo de changes to be committed: mudanças que vão entrar na foto. [terminal]
15. Então, a regra das cores: vermelho é o que mudou, mas ainda não vai na foto. Verde é o que já está preparado, e vai na próxima foto. [compare]
16. E repara no que não aparece na lista: o node modules, o ponto env com a sua senha, e a pasta do login salvo. É o ponto gitignore fazendo o trabalho dele, como na aula vinte e quatro. Eles nunca entram na foto. [cards]
17. Passo três, a foto: git commit traço m, e entre aspas a legenda, tipo meu primeiro projeto Playwright. Commit é a foto, e o traço m é a mensagem dela. [editor]
18. Lendo a resposta: o vinte e quatro d cinco d cinco um é o código dessa foto, cada uma tem o seu. E treze arquivos entraram nela. [traducao]
19. Pra ver a história do projeto: git log traço traço oneline. Uma foto por linha, a mais nova em cima. [editor]
20. E no dia a dia, como fica? Imagina que amanhã você muda o teste da compra. O git status mostra o arquivo em vermelho: modified, modificado. [terminal]
21. Aí é o mesmo ciclo: git add ponto, git commit com uma legenda que diz o que mudou. E o git log já mostra duas fotos. [terminal]
22. E a legenda importa. Ajustes, ou teste, não diz nada. Daqui a um mês, você não lembra. Adiciona teste do carrinho, ou corrige o seletor do login, diz exatamente o que mudou. [traducao]
23. E se você estragou um arquivo e quer ele de volta, do jeito que estava na última foto? Git restore, e o nome do arquivo. Cuidado: o que você mudou desde a última foto se perde. [terminal]
24. Quando fazer um commit? Sempre que uma coisa ficou pronta e funcionando. Terminou um teste e ele passou: commit. Assim, se algo quebrar depois, você tem um ponto salvo bom pra voltar. [cards]
25. Resumindo os comandos: git init, uma vez por projeto. Git status, o que mudou. Git add ponto, prepara. Git commit traço m, a foto com a legenda. E git log, a história. [traducao]
26. Pronto: o seu projeto tem a história dele guardada. Na próxima aula, ela vai pro GitHub, na internet. [passo]
27. Te vejo lá! [endcard]

## Aula 44: GitHub - enviando o projeto
1. O GitHub é um site que guarda projetos Git na internet. É a vitrine de quem trabalha com tecnologia. [bigtext]
2. Pra você, ele resolve três coisas: um backup do projeto, se o computador quebrar. Um lugar onde a equipe trabalha junto. E o seu portfólio: quem for te contratar pode ver o seu código funcionando. [cards]
3. Cria uma conta no github ponto com, se ainda não tiver. Depois clica em New repository. Repositório é a pasta do projeto, lá no GitHub. Dá o nome e cria, sem marcar nenhuma opção, porque o seu projeto já tem os arquivos dele. [github]
4. O GitHub mostra os comandos. No terminal: git branch traço M main. Branch é ramo: uma linha de versões do projeto. Esse comando dá o nome main pro ramo principal. [editor]
5. Depois: git remote add origin, e o endereço do seu repositório. Remote é remoto: avise o Git que existe uma cópia lá no GitHub, chamada origin. [github]
6. E o envio: git push traço u origin main. Push é empurrar: mande o projeto pro GitHub. O traço u liga a sua main com a main de lá, e nas próximas vezes basta git push. [editor]
7. Na primeira vez, o Git pode abrir o navegador pra você entrar na sua conta do GitHub. É normal: faz o login e volta pro terminal. [cards]
8. Atualiza a página do GitHub: seu projeto está lá. E repara: nem o ponto env, nem a pasta do login salvo subiram. [github]
9. E daqui pra frente, o ciclo é sempre esse: add, commit e push. E o GitHub fica igual à sua máquina. [traducao]
10. Na próxima aula: os testes rodando sozinhos no GitHub. [passo]
11. Te vejo lá! [endcard]

## Aula 45: GitHub Actions - os testes rodando sozinhos
1. E se o GitHub rodasse os seus testes sozinho? É isso que o GitHub Actions faz. [bigtext]
2. Por que isso importa? Sem ele, alguém precisa lembrar de rodar os testes. Com ele, toda vez que alguém manda uma mudança pro repositório, os testes rodam sozinhos. [compare]
3. E em muitas empresas, os testes ficam junto com o código do site. Aí cada mudança no site passa pelos testes antes de chegar no cliente. [cards]
4. O Playwright já criou esse arquivo lá no começo: ponto github, workflows, playwright ponto yml. [editor]
5. Lendo em português: quando houver um push ou um pull request na main, use uma máquina Ubuntu, instale tudo e rode os testes. Esses quandos são os gatilhos do arquivo. [traducao]
6. Pull request é quando alguém da equipe pede pra juntar uma mudança na main. Os testes rodam antes, e se ficarem vermelhos, a mudança espera o conserto. [cards]
7. E dá até pra agendar: rodar todo dia de madrugada, mesmo sem ninguém mexer. É assim que um teste aparece falhando às seis da manhã, como na aula do trace. [cards]
8. Só falta uma coisa: o ponto env não foi pro GitHub, então lá os testes não sabem o usuário e a senha. [cards]
9. No GitHub: Settings, Secrets and variables, Actions, New repository secret. Cria o SAUCE underline USER e o SAUCE underline PASSWORD. Secret é segredo: ninguém consegue ver o valor depois. [github]
10. No yml, no passo que roda os testes, um env que entrega esses segredos pros testes. [editor]
11. Traduzindo: SAUCE USER, dois pontos, e cifrão chaves chaves secrets ponto SAUCE USER. Pegue o valor guardado no cofre do GitHub, e entregue pros testes com esse nome, igual o ponto env fazia. [traducao]
12. Manda pro GitHub com git push e abre a aba Actions: olha os testes rodando lá. [gh_actions]
13. Verde: passou. E no fim tem o relatório pra baixar, porque esse arquivo tem o passo que guarda ele. [gh_actions]
14. E se ficar vermelho? O GitHub te avisa por e-mail. Você baixa o relatório, abre o trace, o print e o vídeo, como nas aulas 28 e 30, e anexa no card do bug. [cards]
15. Fechamos o projeto! Tem bônus: testes de API. [passo]
16. Te vejo lá! [endcard]

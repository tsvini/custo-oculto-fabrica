# Roteiros aprovados · Módulo 12 (gerado do roteiro_playwright_m12.py)

## Aula 81: Veio do Cypress? Um mapa das ideias
1. Se você já usou Cypress, várias ideias vão parecer familiares. Mas não pense no Playwright como uma simples troca de comandos. [bigtext]
2. Algumas aproximações ajudam: cy ponto visit lembra page ponto goto. cy ponto contains lembra get by text. should lembra expect. [traducao]
3. Mas o modelo muda. No Playwright você escreve await em cada passo, e os seletores são objetos que você guarda e reaproveita. [bloco_vs]
4. As duas ferramentas resolvem problemas parecidos, com abordagens diferentes. Saber as duas te deixa mais forte no mercado. [bigtext]
5. Te vejo na próxima! [endcard]

## Aula 82: O seu projeto no currículo e na entrevista
1. Agora você tem um projeto de automação. Vamos colocar isso no seu currículo do jeito certo. [bigtext]
2. No currículo, escreve o que você realmente fez: testes de ponta a ponta com Playwright e JavaScript, Page Object e fixtures, testes de API, vários navegadores e execução no GitHub Actions. [traducao]
3. E do nível dois: mock de rede, teste visual, tags e dados em JSON. E o mais importante: dois projetos no GitHub, um deles com um bug que você achou. [traducao]
4. A regra: só coloca o que você consegue explicar numa entrevista. [bigtext]
5. Perguntas que costumam aparecer e que você já sabe responder: o que é auto-wait? Por que preferir seletores pela função? O que é Page Object? [cards]
6. E o que é um teste flaky, que às vezes passa e às vezes falha? E como evitar? [cards]
7. E uma pergunta que quase sempre aparece: conta um bug que você achou. E você tem uma história: a ordenação da Lojinha, achada na mão, antes de automatizar, registrada num card, e depois coberta pelos testes. [cards]
8. Mostrar o projeto funcionando no GitHub ajuda muito a transformar o que está no currículo numa demonstração concreta. [gh_actions]
9. Te vejo na última aula! [endcard]

## Aula 83: Seu projeto pronto pro portfólio e a colinha completa
1. Última aula. Vamos deixar o seu projeto pronto pra quem visitar. [bigtext]
2. Na pasta do projeto, cria um arquivo novo: README ponto md. É a primeira coisa que alguém vê quando abre o seu projeto no GitHub. [menu]
3. Dentro, escreve: o objetivo, as tecnologias, o que precisa instalar, como instalar, e os comandos pra rodar os testes. [editor]
4. Agora, logo embaixo do título, coloca o selinho do GitHub Actions. O próprio GitHub gera o código dele, com o endereço do seu repositório e do seu workflow. [editor]
5. Ele mostra se os testes estão passando. [github]
6. E a sua colinha completa: do primeiro comando ao Page Object, [tela]
7. ao login salvo, ao GitHub Actions e à API. [tela]
8. E a página cinco, com o nível dois inteiro. São cinco páginas: deixa ela aberta enquanto pratica. [tela]
9. Você começou sem saber nada e terminou com dois projetos: o primeiro, com login, compra, API e tudo rodando no GitHub. [cards]
10. E o segundo, que começou num card: os cenários, o bug achado na mão, e a automação que garante que ele não volta. [cards]
11. Próximos passos: pratique, crie novos cenários e mantenha o seu GitHub atualizado. [cards]
12. E se o curso te ajudou, deixa uma avaliação honesta na Udemy. Ela ajuda a melhorar o curso e orienta outros alunos. [bigtext]
13. Até a próxima! [endcard]

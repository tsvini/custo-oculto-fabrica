E se o GitHub rodasse os seus testes sozinho? É isso que o GitHub Actions faz. Por que isso importa? Sem ele, alguém precisa lembrar de rodar os testes. Com ele, toda vez que alguém manda uma mudança pro repositório, os testes rodam sozinhos. E em muitas empresas, os testes ficam junto com o código do site. Aí cada mudança no site passa pelos testes antes de chegar no cliente. O Playwright já criou esse arquivo lá no começo: ponto github, workflows, playwright ponto yml. Lendo em português: quando houver um push ou um pull request na main, use uma máquina Ubuntu, instale tudo e rode os testes. Esses quandos são os gatilhos do arquivo. Pull request é quando alguém da equipe pede pra juntar uma mudança na main. Os testes rodam antes, e se ficarem vermelhos, a mudança espera o conserto. E dá até pra agendar: rodar todo dia de madrugada, mesmo sem ninguém mexer. É assim que um teste aparece falhando às seis da manhã, como na aula do trace. Só falta uma coisa: o ponto env não foi pro GitHub, então lá os testes não sabem o usuário e a senha. No GitHub: Settings, Secrets and variables, Actions, New repository secret. Cria o SAUCE underline USER e o SAUCE underline PASSWORD. Secret é segredo: ninguém consegue ver o valor depois. Agora o yml precisa entregar esses segredos pros testes. Só que esse arquivo já está no GitHub: ele subiu junto com o projeto, na aula quarenta e quatro. Então, onde mudar? Dá pra editar direto no site do GitHub, no lapisinho do arquivo. Mas aí o seu computador fica com a versão antiga. O jeito recomendado: muda no VS Code, e manda pro GitHub com o ciclo da aula quarenta e três. Assim, os dois ficam iguais. Então, no VS Code, abre o playwright ponto yml. No passo que roda os testes, escreve um env que entrega esses segredos pros testes. Traduzindo: SAUCE USER, dois pontos, e cifrão chaves chaves secrets ponto SAUCE USER. Pegue o valor guardado no cofre do GitHub, e entregue pros testes com esse nome, igual o ponto env fazia. Agora manda a mudança pro GitHub, com o ciclo de sempre. Git status: o yml aparece em vermelho, modificado. Git add ponto. Git commit, com uma legenda que diz o que mudou. E git push, que manda pro GitHub. E aqui vem a mágica: esse push é justamente o gatilho do arquivo. Abre a aba Actions no GitHub: olha os testes rodando lá, sozinhos. Verde: passou. E no fim tem o relatório pra baixar, porque esse arquivo tem o passo que guarda ele. E se um dia alguém mudar um arquivo direto no site do GitHub, ou outra pessoa da equipe mandar uma mudança? No seu computador, git pull: puxe as mudanças de lá pra cá. Push manda, pull traz. E se ficar vermelho? O GitHub te avisa por e-mail. Você baixa o relatório, abre o trace, o print e o vídeo, como nas aulas 28 e 30, e anexa no card do bug. Fechamos o projeto! Tem bônus: testes de API. Te vejo lá!

O projeto está pronto. Agora, a pergunta: como guardar ele do jeito certo, de um jeito que dá pra voltar atrás se alguma coisa quebrar? Sem nenhuma ferramenta, o que muita gente faz é copiar a pasta. Projeto final. Projeto final dois. Projeto final agora vai. Depois de uma semana, ninguém sabe qual é qual, nem o que mudou de uma pra outra. O Git resolve isso. Ele é um programa que guarda a história do seu projeto, sem copiar pasta nenhuma. Quando você manda, ele tira uma foto de como os arquivos estão naquele momento, e guarda todas as fotos, em ordem. Cada foto dessas tem um nome: commit. Pensa nos pontos de salvamento de um jogo. Você salva antes da parte difícil, e se der errado, volta pro ponto salvo. E uma confusão muito comum: Git e GitHub não são a mesma coisa. O Git é o programa no seu computador, aquele que você instalou na aula cinco. O GitHub é um site, onde você guarda essa história na internet. Ele é a próxima aula. E pra quem testa, pra que serve? Se você estragar um teste, volta pra versão que funcionava. É assim que a equipe junta o trabalho de todo mundo sem um apagar o do outro. E quase toda vaga de kiuêi pede Git. Salvar com o Git tem sempre três passos. Primeiro, você muda os arquivos, que é o que você já faz. Segundo, o git add: você escolhe o que vai entrar na foto. Terceiro, o git commit: você tira a foto, com uma legenda dizendo o que mudou. Agora na prática. Tudo é feito no terminal do VS Code, aqui embaixo. Antes de começar, confere o caminho antes do cursor: ele tem que terminar com o nome da pasta do projeto, igual na aula oito. Se é a primeira vez que você usa o Git nesse computador, ele precisa saber quem você é, porque toda foto leva o nome de quem tirou. São dois comandos: git config traço traço global user ponto name, e o seu nome entre aspas. E user ponto email, com o seu e-mail. Só uma vez por computador. E uma dica: usa o mesmo e-mail que você vai usar na conta do GitHub, na próxima aula. Assim, lá no seu perfil, cada commit aparece como seu. Agora sim: git init. Init é iniciar. Ele avisa o Git: a partir de agora, guarde a história desta pasta. Ele criou uma pasta escondida chamada ponto git. É lá que ficam todas as fotos. Você não precisa mexer nela, nunca. E o git init é feito uma vez só por projeto. Agora, git status. Status é a situação: o Git te conta o que ele está vendo. Repara: tudo em vermelho, debaixo de untracked files, arquivos não rastreados. Ou seja: o Git viu os arquivos, mas eles ainda não vão na foto. Passo dois: git add ponto. Add é adicionar, e o ponto quer dizer tudo. Prepare todos os arquivos que mudaram pra próxima foto. Roda o git status de novo. Agora está tudo verde, debaixo de changes to be committed: mudanças que vão entrar na foto. Então, a regra das cores: vermelho é o que mudou, mas ainda não vai na foto. Verde é o que já está preparado, e vai na próxima foto. E repara no que não aparece na lista: o node modules, o ponto env com a sua senha, e a pasta do login salvo. É o ponto gitignore fazendo o trabalho dele, como na aula vinte e quatro. Eles nunca entram na foto. Passo três, a foto: git commit traço m, e entre aspas a legenda, tipo meu primeiro projeto Playwright. Commit é a foto, e o traço m é a mensagem dela. Lendo a resposta: o vinte e quatro d cinco d cinco um é o código dessa foto, cada uma tem o seu. E treze arquivos entraram nela. Pra ver a história do projeto: git log traço traço oneline. Uma foto por linha, a mais nova em cima. E no dia a dia, como fica? Imagina que amanhã você muda o teste da compra. O git status mostra o arquivo em vermelho: modified, modificado. Aí é o mesmo ciclo: git add ponto, git commit com uma legenda que diz o que mudou. E o git log já mostra duas fotos. E a legenda importa. Ajustes, ou teste, não diz nada. Daqui a um mês, você não lembra. Adiciona teste do carrinho, ou corrige o seletor do login, diz exatamente o que mudou. E se você estragou um arquivo e quer ele de volta, do jeito que estava na última foto? Git restore, e o nome do arquivo. Cuidado: o que você mudou desde a última foto se perde. Quando fazer um commit? Sempre que uma coisa ficou pronta e funcionando. Terminou um teste e ele passou: commit. Assim, se algo quebrar depois, você tem um ponto salvo bom pra voltar. Resumindo os comandos: git init, uma vez por projeto. Git status, o que mudou. Git add ponto, prepara. Git commit traço m, a foto com a legenda. E git log, a história. Pronto: o seu projeto tem a história dele guardada. Na próxima aula, ela vai pro GitHub, na internet. Te vejo lá!
